## 1. Executive summary

### How Qmatch should make money

Qmatch should use a **premium freemium** model: free users get a complete, usable connection loop (assessments, limited discovery, mutual match, chat, safety). Paying users unlock **deeper compatibility intelligence**, **discovery control**, and **premium visibility** — not access to “better humans.”

Revenue mix (target):

1. **Primary:** Subscription — **Qmatch Resonance** (main paid tier)
2. **Secondary:** Light consumables — Super Resonance, Boost/Spotlight (and later Deep Insight)
3. **Later:** Mid-tier Plus and Orbit/Platinum only after Resonance proves value

### Why freemium makes sense

- Dating/compatibility apps need **network density**; hard paywalls starve supply of profiles.
- Assessments (IQ/EQ/Frequency) are the product’s **trust and differentiation engine** — they should stay reachable free so users feel the brand before paying.
- Freemium in *spirit* (limits + insight depth) is familiar globally; Qmatch differentiates by **what is sold**, not by inventing a novel payment UX.

### Why Qmatch must not monetize via a crude “IQ gate”

Selling “access to high-IQ people,” ranking users as low/high IQ for status, or implying clinical IQ diagnosis would:

- Feel exploitative and classist
- Conflict with Premium Cosmic Minimal (trustworthy / emotional)
- Create store, PR, and ethics risk
- Reduce Qmatch to a crude swipe clone with score-snobbery

**Instead:** monetize **compatibility range**, **thinking-style / emotional-depth / frequency alignment**, **insight depth**, and **discovery control**.

### How monetization supports Premium Cosmic Minimal

| Do | Don’t |
|----|-------|
| Unlock deeper understanding | Block basic belonging |
| Elegant glass “insight locked” cards | Loud neon paywalls / countdown guilt |
| Cosmic language: resonance, alignment, connection map | “Upgrade to see hot people” / IQ ladders |
| Free CosmicProfileHero + basic compatibility | Paywall the human face / identity hero |
| Soft limits with clear daily resets | Infinite dark patterns |

## 3. Qmatch monetization pillars

### A. Discovery control

Expand *who* and *how often* you can explore — quotas, range, rewind, top matches — without implying humans are behind a paywall by IQ label.

### B. Deep compatibility insight

Upgrade from a **basic compatibility score** to reports, shared-values analysis, resonance timeline, connection-map depth. Analytical **second**, premium **first** in presentation.

### C. Premium visibility / attention

Boost, Spotlight, Super Resonance, later Orbit frame — temporary or intentional attention, never “pay to access smarter people.”

### D. Advanced IQ/EQ/Frequency interpretation

Filters and explanations framed as:

- thinking style alignment
- cognitive compatibility
- emotional depth
- frequency resonance
- expanded compatibility range

Not: IQ scoreboards or gated castes.

### E. Trust, safety, and quality matching

Safety/reporting/settings stay **free forever**. Premium may add *quality* tools (better filters, intentional connect) but never sell safety itself.

## 6. Ethical rules — IQ / EQ / Frequency monetization

**Explicit rules:**

1. **Do not** sell access to “higher IQ people.”
2. **Do not** label users as low/high IQ in a humiliating or status-ranking way.
3. **Do not** imply clinical or official IQ diagnosis / medical assessment.
4. Treat Qmatch IQ as a **reasoning / thinking-style compatibility signal**, not a human worth score.
5. **Monetize range controls and insight depth**, not human ranking.
6. Prefer language:

   - thinking style alignment
   - cognitive compatibility
   - emotional depth
   - frequency resonance
   - expanded compatibility range
   - deep insight
   - connection map
   - resonance

7. EQ / Frequency must not become “emotional maturity shaming” either — same principle: **alignment**, not castes.
8. Free users keep assessment access and a basic score so the brand promise is not held hostage.
9. Marketing and paywalls must never imply Qmatch is an IQ test vendor or Mensa-style gate.

## 9. Future technical architecture *(plan only — do not implement now)*

### Product catalog (suggested IDs)

**Subscriptions**

| Product ID (example) | Tier |
|----------------------|------|
| `qmatch_resonance_monthly` | Resonance monthly |
| `qmatch_resonance_yearly` | Resonance yearly (discount) |
| Later: `qmatch_plus_monthly` | Plus |
| Later: `qmatch_orbit_monthly` | Orbit |

**Consumables**

| Product ID (example) | Item |
|----------------------|------|
| `qmatch_super_resonance_1` | Super Resonance ×1 (or pack SKUs) |
| `qmatch_boost_1` | Boost / Spotlight ×1 |
| Later: `qmatch_deep_insight_1` | Deep Insight Report |

### Entitlement model

- **Source of truth:** backend (Cloud Functions + Firestore), **not** client flags alone
- Client reads entitlements for UI; server grants after verified purchase
- Features map: `see_who_aligned`, `advanced_filters`, `deep_reports`, `rewind`, credit balances, etc.

### Why client-only entitlement is insecure

Any `isPremium = true` written only from the device can be forged. Attackers unlock Resonance without paying. **Always verify** with Google Play Developer API / App Store Server API (or trusted receipt validation) server-side.

### Suggested Firestore model

```
users/{uid}
  premiumTier          // "free" | "plus" | "resonance" | "orbit"
  premiumExpiresAt      // timestamp | null
  boostCredits          // int
  superResonanceCredits // int
  deepInsightCredits    // int

purchases/{purchaseId}
  uid
  platform              // "android" | "ios"
  productId
  purchaseToken         // platform token / transaction id (store securely)
  status                // "active" | "expired" | "refunded" | "pending"
  createdAt
  expiresAt             // for subscriptions

entitlements/{uid}
  tier
  features              // map or list of feature flags
  expiresAt
```

Security notes (later):

- Clients must **not** write `premiumTier` / credits / entitlements arbitrarily (rules lock to admin/Functions)
- Purchase tokens are sensitive — minimize client exposure; prefer Functions-mediated verify

### Backend responsibilities

| Concern | Approach |
|---------|----------|
| Purchase verification | Cloud Functions (or other backend) |
| Restore purchases | Re-query store + rehydrate entitlements |
| Subscription lifecycle | Renew / expire / grace / account hold |
| Cancellation | Store-managed; app reflects entitlement end |
| Refunds | Webhook / RTDN (Play) / App Store notifications → revoke |
| Cross-platform | Map same `uid` entitlements; avoid double-grant bugs |

### Client libraries (later phases only)

- Android: Google Play Billing
- iOS: StoreKit / `in_app_purchase` (or equivalent)
- **Not in this phase:** no package adds

Current launch stance (answer sheet): **no payments / financial info**; no ads/tracking SDKs.

**When monetization ships, update:**

- App Store Privacy answers

| Category | Examples | Typical purpose |
|----------|----------|-----------------|
| Purchase history | Orders, product IDs | App functionality / account |
| Subscription status | Active tier, expiry | Functionality |
